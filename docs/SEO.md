# SEO

How search indexing works on pushkalgupta.com, what was wrong, and what still is.

The site is a monorepo published as one GitHub Pages site: a static root landing
page, static folders (`blog/`, `chess/`, `PG.Quiz/`, …), and three Vite SPAs
served from their `dist/` sub-paths. There is no server, so everything here has
to work as static files.

---

## The rules

**One canonical URL per page.** Every indexable page declares
`<link rel="canonical">` with its absolute URL. Anything that shows the same
content at a second address (`/PG/main.html`, `/blog/<slug>/light.html`) points
its canonical at the real one and carries `noindex, follow`.

**Never both `noindex` and a sitemap entry.** Google reads that as a
contradiction and reports it. `scripts/generate-sitemap.mjs` only lists
canonical, indexable URLs.

**Never `Disallow` a page you also want de-indexed.** A blocked page can't be
fetched, so Google never sees the `noindex` or the canonical and the duplicate
just floats. `robots.txt` deliberately leaves `/blog/*/light.html` crawlable for
exactly this reason.

**Navigation must be real `<a href>`.** A `<div onclick="location.href=…">` is
invisible to a crawler — it is not a link, so nothing on the other side gets
discovered. This is what kept the entire site's link graph hidden.

**Content must be in the HTML, not painted in by JS.** Googlebot does render
JavaScript, but rendering is queued separately and is never as reliable as
markup that is simply there.

## What was wrong (fixed)

| Problem | Effect | Fix |
| --- | --- | --- |
| Root `/` was a 140-byte `<meta http-equiv="refresh">` stub | The domain's most important URL had no title, no description, no content, no links. Nothing to rank. | `/index.html` is now the real landing page — `<h1>`, intro copy, and the project list as static HTML |
| No `robots.txt`, no `sitemap.xml` | Nothing told Google what exists or where to start | Both added; sitemap generated by script |
| Project cards were `<div onclick=…>` | No crawlable path from the homepage to any project | Cards are `<a href>` |
| Blog post list was `<div onclick=…>` | No crawlable path to any essay | List items are `<a href>` to each essay's own URL |
| Essays existed only as `*-dark.html` / `*-light.html` pairs | Two byte-identical copies of every essay competing with each other, neither linked | Moved to `/blog/<slug>/` (canonical) + `/blog/<slug>/light.html` (`noindex`, canonical → the former) |
| Essays had no description, canonical, OG tags, or dates; two had no `<title>` at all | Google had to invent a snippet | Full metadata + `BlogPosting` JSON-LD on each |
| SPA shells had no canonical/OG/structured data; onlineChess had only `<title>PG.Chess</title>` | Poor snippets, no rich results | Full metadata + `WebApplication` JSON-LD on all three |
| SPAs render blank without JS | Nothing for a crawler to read before the bundle runs | `<noscript>` block on each with a real description and links |
| `/favicon.svg`, `/site.webmanifest`, `/images/logo.png` referenced root-absolute from sub-path apps | 404 in production — no favicon anywhere | Made relative (`./…`), matching Vite's `base: ''` |
| No `404.html` | GitHub Pages' default 404, no way back into the site | Custom 404 with `noindex` and links to every section |
| `PGHub/CLAUDE.md`, QA backlogs, `docs/`, `supabase/` all publicly served | Internal notes live and indexable; wasted crawl budget | Excluded in the deploy workflow, plus `robots.txt` rules |
| Blog post list was painted in by `blog.js` | Zero essays were reachable by a crawler that doesn't run JS | Post list is static HTML in `blog/index.html`; JS only upgrades the links into the reader |
| Blog index lived at `/blog/blog.html` | Ugly URL for the section's landing page | Moved to `/blog/`; the old path is a `noindex` redirect stub |
| Essays were orphans — reachable only from the index | Weak internal link graph; a reader from search had nowhere to go | "More essays" block on every essay linking to all the others, plus `BreadcrumbList` JSON-LD |
| No feed | No discovery channel that doesn't go through Google | `blog/feed.xml` (RSS 2.0), generated, linked via `<link rel="alternate">` and a visible link |
| 21 coursework demos in `PG.Web_Basics/` were indexable | 10–360 words each, several with duplicate titles — thin content dragging on the whole domain | `noindex, follow` on all of them; only the section index stays indexable |
| Supabase's 120KB bundle was a synchronous `<script>` in the blog index's `<head>` | Render-blocking on a page whose content needs no JS | Both scripts `defer`, on the blog and the homepage |
| Essays had no `preconnect` to the font origin | Full DNS+TCP+TLS before the render-blocking font CSS could even be requested | `preconnect` to `fonts.googleapis.com` / `fonts.gstatic.com` |
| PG.Play overwrote `document.title` with "22 playable titles" | The *rendered* title is what Google indexes, so the static keyword-carrying title was being thrown away | Runtime title keeps the keywords: "22 free browser games, no download" |
| `public/` published alongside `dist/` for all three apps | ~320MB of exact duplicate assets, each reachable at two URLs | Excluded in the workflow — published site went from 773MB to 417MB |
| Homepage ended abruptly after the project list | No consistent link block on the most-crawled page | Footer with grouped links to every section plus the feed |

## What is still wrong: hash routing

**All three SPAs use `HashRouter`.** Every in-app route lives after a `#`:

    https://pushkalgupta.com/PGHub/dist/#/learn/graphs/dijkstra

Search engines discard the fragment. That URL and `…/dist/#/practice` and
`…/dist/#/forge/cuda` are, to Google, **the same single URL**. PG.Hub's roadmap,
thousands of problems, ML lessons and visualisations — the site's entire body of
rankable content — currently compete for one indexed page. Same for every PG.Play
game and every PG.Chess section.

This is by far the largest remaining lever, and nothing in the metadata layer can
work around it. Fixing it means one of:

1. **`BrowserRouter` + build-time prerender.** Switch each app to real paths,
   then render every route to a static `dist/<route>/index.html` at build time
   (headless-browser prerender step in the Vite build). GitHub Pages then serves
   real HTML at real URLs with a real 200. Correct and complete, but it touches
   routing, OAuth redirect URLs, and the deploy pipeline in all three apps — and
   PG.Hub's problem/lesson routes are Supabase-backed, so the prerender needs
   database access at build time.

2. **`BrowserRouter` + `404.html` SPA fallback.** The classic GitHub Pages trick.
   Fixes deep links for *users*, but the server still answers 404, so it does
   **not** get the routes indexed. Not a solution to this problem.

3. **Static content pages for the highest-value routes only.** Generate genuine
   full-text HTML pages for, say, the DSA tutorial topics and ML lessons whose
   content already lives in `PGHub/src/content`, each linking into the app. Much
   smaller change than (1). Only worth doing with the *complete* content on the
   page — a stub that exists to catch a query and bounce you into the app is a
   doorway page, and Google penalises those.

Option 1 is the real answer; option 3 is the cheap partial one. Both are larger
than a metadata pass, which is why neither is done here.

## Maintenance

**Adding or renaming a page:**

1. Add it to `index.html` (or wherever it should be linked from) as a real `<a href>`.
2. Give it `<title>`, `<meta name="description">`, `<link rel="canonical">`, OG tags.
3. Add it to the `PAGES` list in `scripts/generate-sitemap.mjs`.
4. Run `node scripts/generate-sitemap.mjs` and commit the regenerated `sitemap.xml`.

**Adding an essay** — the post list exists in four places that must agree:

1. `blog/index.html` — the static `<a class="feed-item" data-post-id="…">` row.
2. `blog/blog.js` — the `POSTS` array (`id` and `slug` must match the markup).
3. `scripts/generate-sitemap.mjs` and `scripts/generate-feed.mjs` — then re-run both.
4. The "More essays" block at the foot of every *other* essay.

If the markup and `POSTS` drift, `blog.js` leaves the link alone rather than
swallowing the click, so the essay still opens — just without the comments panel.

The generator fails loudly if a listed URL's source file is missing, so a rename
that forgets step 3 breaks the build rather than silently shipping a 404 in the
sitemap.

**`lastmod`** comes from each file's last commit date, not from "now" — stamping
today's date on every URL every run teaches Google to ignore the field.

## Search Console

After the first deploy carrying these changes:

1. **Submit the sitemap** — Search Console → Sitemaps → `sitemap.xml`.
2. **Request indexing for `/`** via the URL Inspection tool. It's a brand-new
   page at the site's most important URL; don't wait for a natural crawl.
3. **Re-inspect the old essay URLs.** `/blog/ai-cage-dark.html` and friends no
   longer exist. They will drop out on their own — no redirect stubs were left,
   since nothing external links to them.
4. **Expect the Pages report to change shape.** Pages that were "Crawled –
   currently not indexed" (the markdown files, the redirect stub) should move to
   excluded-by-robots or 404. That is the intended outcome, not a regression.
5. **Watch `/PGHub/dist/` in the Pages report.** It will stay a single indexed
   URL until the hash-routing issue above is addressed.
